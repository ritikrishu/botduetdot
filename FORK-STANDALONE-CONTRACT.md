on Google Play — that never talks to T3 Tools Inc. services, uses none of their identifiers/marks,
coexists with the official app on the same Mac and phone, keeps the MIT notice, and stays cheap to merge
with upstream releases.

### 2.4 Scheme policy

Standalone **registers, parses and emits only its own schemes** (`botduetdot`, `botduetdot-dev`,
`botduetdot-preview`) — on macOS (`CFBundleURLTypes`, `getDesktopScheme`), Android (intent filters),
shared parsers (`promptLinks.ts`, `remote.ts`, `providerAuthReturnUrl.ts`, `codexAuthHandoff.ts`) and
mobile (`pairing.ts`, `App.tsx`). Registration is what steals links from the official app; parsing
upstream schemes would only make a BotDuetDot window act on links meant for T3 Code (argv, pasted links),
so it is not done either. The one cross-product allowance is CORS: the server accepts the official
renderer origins `t3code://app`/`t3code-dev://app` (S9), so the official desktop app can add a BotDuetDot
server as a remote environment. Shared helpers take the scheme set from `brandAppSchemes(BRAND)`; the
`t3code(?:-[a-z]+)?:` regexes (`promptLinks.ts:184`, `remote.ts:7`) become `brandAppSchemePattern(BRAND)`.
**r4 amendment (orchestrator, from T2b) — applies to every seam:** never widen what an upstream site
accepts. Where upstream checks a narrower set than `brandAppSchemePattern` (e.g. S19
`providerAuthReturnUrl.ts:7` accepts only `t3code:`/`t3code-dev:`), derive the same narrow set from brand
fields (`[brand.schemes.production, brand.schemes.development]` → upstream `t3code:`/`t3code-dev:`
unchanged; standalone `botduetdot:`/`botduetdot-dev:`), and pin both in tests, including rejection of
the other product's schemes and of arbitrary suffixes (`t3code-attacker:`). Use
`brandAppSchemePattern`/`isBrandAppProtocol` only where upstream already used the open
`t3code(?:-[a-z]+)?:` pattern.

**r3 amendment (orchestrator, from T1):** `brandAppSchemePattern(UPSTREAM_BRAND)` must be exactly today's
`/^t3code(?:-[a-z]+)?:$/` (upstream also accepts e.g. `t3code-nightly:`), so upstream behaviour is
unchanged; `brandAppSchemePattern(STANDALONE_BRAND)` matches only the three BotDuetDot schemes.
`isBrandAppProtocol` delegates to `brandAppSchemePattern`, so the same split applies to it. Tests pin both.
`schemePolicy` selects the derivation: upstream `"prefix"` uses the escaped profile slug plus
`(?:-[a-z]+)?`; standalone `"exact"` uses only the three escaped profile schemes. No upstream brand
literal lives in `brand.ts`; tests pin the upstream pattern's `.source` and empty `.flags`.

### 5.1 Desktop (macOS)

Versioning: `0.1.9-botduetdot.<n>`. Classified as stable by `updateChannels.ts:2`, `cliReleaseChannelOf`
(`cliRelease.ts:88-91`) and `resolveDesktopUpdateChannel`; `versionSkew.ts:43-67` compares only the core
version; semver orders successive builds. Tag `v<version>`, published as a full release (feed uses
`releaseType: release` + `/releases/latest`). UNVERIFIED: electron-updater with a prerelease-shaped current
version (`DesktopUpdates.ts:518-530` forces channel `latest`, `allowPrerelease=false`) → verify with
`--mock-updates` + `vp run start:mock-update-server` before the first public release; fallback plain semver.

Wrapper `scripts/standalone/release-desktop-mac.ts` (owner's Apple-silicon Mac):

```bash
export PATH="$HOME/.local/share/vite-plus/bin:$PATH"
export T3CODE_BRAND=standalone
# identity: Developer ID Application in the login keychain, or CSC_LINK + CSC_KEY_PASSWORD
export APPLE_API_KEY=$HOME/keys/AuthKey_<KEY_ID>.p8 APPLE_API_KEY_ID=<KEY_ID> APPLE_API_ISSUER=<ISSUER_UUID>
#   (or APPLE_KEYCHAIN_PROFILE=botduetdot-notary from `xcrun notarytool store-credentials`)
node scripts/standalone/release-desktop-mac.ts --version 0.1.9-botduetdot.1 [--publish]
```

Steps (any failure aborts; nothing is uploaded unless every step passed):

1. Preflight: clean git tree (record commit); version matches `^\d+\.\d+\.\d+-botduetdot\.\d+$`; no
   forbidden env (§2.2); exactly one complete notarization credential set (electron-builder would otherwise
   skip notarization with only a warning, `MacTargetHelper.js:262-266`); a `Developer ID Application`
   identity is available; `gh release view v<ver> --repo ritikrishu/botduetdot` must not exist.
2. Build: `vp run dist:desktop:artifact --platform mac --target dmg --arch arm64 --build-version <ver> --signed --output-dir release`.
   Output: `BotDuetDot-<ver>-arm64.dmg` + `.blockmap`, `BotDuetDot-<ver>-arm64.zip` + `.blockmap` (the
   Squirrel.Mac update payload), `latest-mac.yml`. Record sha256 of each.
3. Verify the **`.app` inside both containers** (mount `hdiutil attach -nobrowse -readonly -mountpoint <tmp>`;
   ZIP via `ditto -x -k`):
   `codesign --verify --deep --strict --verbose=2 <app>`; `codesign -dv --verbose=4 <app>` (Identifier
   `com.ritikrishu.botduetdot`, TeamIdentifier = owner, `Authority=Developer ID Application: …`,
   hardened runtime flag); `xcrun stapler validate <app>`; `spctl -a -vvv -t exec <app>` →
   `accepted … source=Notarized Developer ID`; both apps have the same CDHash.
4. Run `check-brand-leaks.ts --mac-release release/` (§5.3) on those exact files.
5. Publish (`--publish`): re-check sha256s, then
   `gh release create v<ver> --repo ritikrishu/botduetdot --title "BotDuetDot <ver>" --notes-file <notes> <the five files>`.
   Always pass `--repo` (this checkout's `gh` default resolves to upstream, §7). The repo must stay
   public so the feed needs no token.

DMG container (finding 5): electron-builder notarizes and staples the `.app` before packaging
(`macPackager.js:347` → `@electron/notarize` staples `appPath`), so the stapled ticket travels inside the
DMG and the ZIP. **Recommendation for v1: do not notarize the DMG** — upstream ships the electron-builder
DMG unchanged (`.github/workflows/release-desktop.yml:711-723,778`), Gatekeeper assesses the stapled app
on first launch (works offline), and modifying the DMG would make the `latest-mac.yml` hash and `.blockmap`
stale. `spctl -t install` is for installer packages (`man spctl`), and the DMG assessment
(`spctl -a -vvv -t open --context context:primary-signature <dmg>`) rejects an unsigned DMG by design, so
it is not a v1 check. Optional hardening (v1.1, in the same wrapper, after step 3): `codesign --sign
"Developer ID Application: …" --timestamp <dmg>` → `xcrun notarytool submit <dmg> --key … --key-id …
--issuer … --wait` → `xcrun stapler staple <dmg>` → recompute the DMG `sha512`/`size` in
`latest-mac.yml` and regenerate the `.dmg.blockmap` → validate with `xcrun stapler validate <dmg>` and the
`-t open --context context:primary-signature` assessment.

v1 ships arm64 only (CLI SEA doesn't support darwin-x64). For Intel later: build x64 and merge manifests
with `node scripts/merge-update-manifests.ts --platform mac` (as `release.yml:884-923`), or `--arch universal`.
Not needed with `macPasskeys: false`: `T3CODE_APPLE_TEAM_ID`, `T3CODE_MACOS_PROVISIONING_PROFILE`,
`T3CODE_CLERK_PASSKEY_RP_DOMAINS`.

GitHub Actions: **not required for v1.** Optional v1.1: `.github/workflows/standalone-desktop-release.yml`
(`workflow_dispatch`, `if: github.repository == 'ritikrishu/botduetdot'`, `macos-15`, `contents: write`)
running the same wrapper with secrets `CSC_LINK`, `CSC_KEY_PASSWORD`, `APPLE_API_KEY` (p8 contents written to
a temp file like `release-desktop.yml:619-622`), `APPLE_API_KEY_ID`, `APPLE_API_ISSUER`.
